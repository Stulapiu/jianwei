# 见微 · 校园微治理平台

> 见微知著。
> 一张照片，让一处破损被看见、被派人、被解决。

一个面向校园的众包式设施微治理系统：学生路过发现路灯坏了、井盖缺失、路面积水，拍一张照，
系统自动判断这条信息值不值得派人、该归哪个部门，然后进工单池。

落地场景：**郑州大学主校区**（113.5315, 34.8172）。

## 二、打开方式

### 方式 A：双击单文件（最快）

```
dist/见微-管理后台.html
dist/见微-用户端.html
```

不依赖任何服务器。但 `file://` 协议有两个天然限制：**拿不到 GPS 定位**、**地图瓦片可能被跨域拦截**。
所以用户端会自动退回到「演示点位」模式，地图上仍然有点，只是不会飞到你当前位置。

### 方式 B：起本地服务（完整功能，推荐）

```bash
node server/proxy.mjs
```

然后打开 <http://localhost:8787>。

这一个命令同时解决四件事：

1. **静态托管** —— 页面跑在 `http://` 而不是 `file://`，`navigator.geolocation` 才被允许
2. **转发 DeepSeek** —— 密钥不能写进前端（静态站的 JS 谁都能看），转发层让它只留在服务端
3. **保管密钥** —— Key 只在本机环境变量里，不进前端代码、不进仓库
4. **离线兜底** —— 不配 Key 也能跑，前端自动回落到本地规则引擎

带上 DeepSeek Key 启动：

```bash
# Windows CMD
set DEEPSEEK_API_KEY=sk-xxxx && node server/proxy.mjs
# PowerShell
$env:DEEPSEEK_API_KEY="sk-xxxx"; node server/proxy.mjs
# bash
DEEPSEEK_API_KEY=sk-xxxx node server/proxy.mjs
```

健康检查：<http://localhost:8787/health> 返回 `{ ok, hasKey, vision, model }`。
`vision: true` 表示模型能直接看图——前端据此决定是否把原图一起发过去。

### 方式 C：纯静态托管

`h5-web/` 和 `admin-web/` 都是纯静态目录，扔到 GitHub Pages / 任意静态空间就能访问，相对路径已配好。
没有后端时 AI 自动走规则模式，功能不缺，只是不通真模型。

## 三、身份体系：不登录也能用

众包系统绕不开一个问题——**不知道是谁报的，就没有信用可言**。所以做了三种身份，而不是强制登录：

| 身份 | 进入方式 | 得到什么 |
|---|---|---|
| 学号登录 | 8–12 位学号，一键进入（真实环境接教务 CAS） | 信用分、积分、徽章长期累积 |
| 手机号登录 | 11 位手机号 + 6 位验证码 | 同上，适合校外居民 |
| 游客 | 一个按钮 | 可上报、可查进度；信用只存在本机 |

游客靠 localStorage 里的设备标识（`DEV-XXXXXX`）被"认出来"，所以**同一台设备重复报同一处只合并、不升级**——刷不动。

### 3.1 三套数字，互相不能替代

| 维度 | 范围 | 管什么 | 规则 |
|---|---|---|---|
| **信用分** | 0–100 | 资格 | 起始 70；有效 +2（合并 +1）；复核判定无效 −5；低于 60 强制人工复核 |
| **积分** | 只增 | 收益 | **后勤办结才发**：20–90 分，按紧急度 × 类型 × 上报方式；乱报 −20 |
| **账号权重** | 0.3–1.5 | 投票权 | 有效 +0.02；乱报 ×0.82；**低于 0.6 不计入"反馈人数"** |

一句话：**信用分决定别人信不信你，积分决定你得了多少好处，权重决定你的一票算不算数。**

只做一个"积分"的系统，最后一定既当不了信用、也当不了钱。拆开才对得上。

### 3.1.1 积分为什么不在提交时发

AI 判"有效"只证明这张照片像那么回事，不证明现场真有一盏坏灯。当场发钱，奖励的是"会拍照"这件事，刷单也就有了动机：找面脏墙换十个角度拍，照样拿分。

所以钱压在最后一环——**后勤到场、核实、处理完，才结算**（`shared/payout.js`）。到这一步，乱报的人拿不到任何东西，因为他报的地方根本没东西可修。

| 星级 | 基础分 | | 类型系数 | | 上报方式 | |
|---|---|---|---|---|---|---|
| 1 星 | 20 | | 安全隐患 | ×1.2 | 独立发现 | ×1 |
| 2 星 | 30 | | 道路破损 | ×1.1 | 帮别人确认同一处 | ×0.6 |
| 3 星 | 45 | | 给排水 / 设施 / 网络 | ×1.05 | 同一处重复上报 | ×0.4 |
| 4 星 | 65 | | 照明 / 卫生 / 交通 | ×1 | 转人工后核实为真 | ×0.75 |
| 5 星 | 90 | | 绿化 | ×0.95 | | |

结果取整到 5 的倍数。提交那一刻就算好、写进工单（`estPoints`），办结时按这个数发 —— 以后调价不会回头改已经报上去的单子，用户看到的"预计 +65"和到账数字永远一致。

界面上三处体现这件事：上报页提交前有档位条（20/30/45/65/90，按所选类型实时换算）、成功页写"待发放 +80"而不是"积分 +80"、我的上报列表在办结后变成绿色的"积分 +80 已到账"。

### 3.1.2 积分花在哪

只有两个出口，都不编新故事：

| 出口 | 内容 |
|---|---|
| **商城** | 头像框 3 件（青叶 / 路灯 / 测绘）、称号 3 个（见习巡街人 / 夜巡者 / 见微知著），60–520 分 |
| **抽奖** | 30 分一次，池子里全是商城不卖的东西：流萤框、守夜人、50 / 120 积分、再来一次、谢谢参与 |

两个池子严格不重叠 —— `Rewards.verify()` 启动时按 id 和名称各查一遍重，抽到的和买到的不会撞车；抽到已拥有的自动折 60 分，不让人白抽。

**曾经做过一版宠物养成，后来整个删掉了。** 那是另一个游戏：饱食度、升级曲线、衣橱、专属道具，跟"上报—派单—办结"这条链没有因果关系，挂在这里只会显得积分体系是靠养成撑着的。积分有两个出口已经够用，而且这两个都能直接挂在上报这件事上讲清楚。

### 3.2 查询编码

游客提交后拿不到账号，但拿得到一串编码：

```
JW-8F3K2M
```

- 字符集去掉了 `0/O`、`1/I`，口头念、手抄都不容易错
- 输入时自动转大写、去空格，漏了 `JW-` 前缀也能识别
- 一条编码对应一张工单，与身份无关，**换台设备也能查**
- 演示写死两条：`JW-8F3K2M`（处理中）、`JW-Q7M4TP`（已解决）

### 3.3 桌面上的定位问题

桌面浏览器打开手机端页面定位不了，**不是 bug**：

- `file://` 协议下浏览器直接禁用 `navigator.geolocation`（规范要求）
- 只有 `https` 或 `localhost` 才允许
- 台式机没有 GPS，浏览器退化成网络定位，校园网下常超时

所以做了三层兜底：定位中给明确状态 → 失败时弹出**常驻**提示条（不是两秒就消失的 toast）→
提供「在地图上选点」，点哪里就是哪里，坐标立刻回填。定位永远失败也不影响提交。

## 四、AI 是怎么判的

项目里叫它 **哨兵智能体（Sentinel Agent）**，`shared/agent.js`，约 600 行，零依赖。

它的核心立场：**AI 可以建议，但不能替用户决定**。所以只有两道闸门，且永远留人工出口。

### 闸门一：视觉质量（本地算，不花钱）

上传的照片在浏览器里解码成 canvas，逐指标计算：

| 指标 | 算法 | 用途 |
|---|---|---|
| 清晰度 | 16px 分块拉普拉斯方差，取**前 30% 的均值** | 判断是否拍糊 |
| 亮度 | 平均 luma | 判断是否全黑/过曝 |
| 平坦区占比 | 低梯度像素比例 | 判断是否拍到一片天空或墙面 |
| 边缘密度 | Sobel 梯度均值 | 判断画面里有没有实体 |

清晰度这里有个坑值得说：如果用**全图**方差，一张「上半是天空、下半是井盖」的照片会被判成模糊——
因为天空占了 60% 的平坦像素，把整体方差拉低了。改成「分块计算 + 取最清晰那 30% 的块」，
才符合人眼直觉：**只要有一块是实的，这张照片就是实的**。

阈值来自 `tools/probe-photo.html` 的实测标定：

```js
var THRESH = { blur: 25, dark: 0.10, blackout: 0.035, overexposed: 0.94,
               flat: 0.88, flatEdge: 0.012, noEdge: 0.004, noInfoSharp: 12 };
```

画质问题分两类，处置方式完全不同：

| 类型 | 触发条件 | 处置 |
|---|---|---|
| **hard** | 边缘密度 ≈ 0 且清晰度极低（`blank`）、几乎全黑（`blackout`）、全白（`overexposed`）、又平又糊（`flat`） | 直接拒绝，提示重拍 |
| **soft** | 拍糊了（`blur`）、夜里偏暗（`dark`） | 放行，但工单标「画质存疑 · 待人工复核」，后台抽屉里有黄色提示 |

`blank` 是这轮补的：镜头被手指挡住、对着桌面或墙面拍，指标会呈现「平坦区 1.000、边缘密度 0.000、清晰度个位数」。这类图不是"拍得不好"，是**没拍到任何东西**，模型也救不回来，必须拦。

之前所有画质原因都被无条件放行（理由是不想让夜景被误杀），结果是一片均匀的糊图也能进工单池——闸门一等于不存在。现在按"画面里有没有东西"分开处理，宁可让模型多看一眼，也不让空白图混过去。

### 闸门二：内容一致性（DeepSeek 视觉判定）

**原图 + 图像指标 + 用户选的类型 + 用户描述**一起发给 `deepseek-flash`（原生支持图片输入，
base64 内联，单图最多计费 1024 token），让它回答四件事：

1. 画面里实际是什么（`seen` 字段，只准写所见，不准写推断）
2. 是不是一处公共设施问题（还是风景、人像、截图）
3. 与所选类型是否一致
4. 严重度几星（1–5）、一句话摘要、一句处置建议

`seen` 是这道闸门的关键设计：模型必须先用一句话描述画面，这句话会原样存进工单、
在后台抽屉里显示。编不出来的东西它说不圆——比一句"通过/不通过"可信得多。

**否决权按"看没看到图"分配**：

| 情况 | 谁说了算 |
|---|---|
| 有原图（实拍 jpeg/png/webp） | 模型有第一手证据，它的判断直接采纳 |
| 没原图（演示用的 SVG 插画、或未开启视觉） | 模型只拿到统计量，判断降级为"建议"，仍以本地规则为准 |

早期版本一律把模型判断降级成建议，理由是"它看不到图"。接上视觉之后这条前提不成立了，
所以改成按证据来源分配——否则等于"让它看，又不信它"。

对于语义边界模糊的词（比如「井盖缺失」既像安全隐患又像设施损坏），`shared/domain.js` 里给每个类型挂了
`also: []` 兼容列表，用户选哪个都不会被判成类型错配。

### 类型选错不驳回：让模型自己改

这一条改过一次方向。早先的逻辑是"类型与画面不符 → 驳回，让用户重选"，
想的是"分类准确才好派单"。实际跑下来发现两个问题：

1. **点错按钮是常事**，为此驳回一次等于让人把整张表重填一遍，多数人这时候就关掉不报了；
2. 驳回给的是压力，不是信息——用户并不知道该选哪一类。

现在的做法：类型不对，模型直接给出它认为正确的 `type`，前端**静默替换**，不弹窗、不提示、不告诉用户改了什么。
理由很直白：**该改的是分类，不是人的态度**。用户可以事后在工单详情里看到"类型修正：照明路灯 → 安全隐患"。

只有一种情况会让用户停下来看——**描述与画面真矛盾**（见下）。

### 照片什么时候必须传

一开始是"一律必传"，被问了一句就站不住了：**校园网很卡怎么拍？**

现在的判定标准不是"这类问题重不重要"，而是**这张图能不能证明问题存在**：

| 能证明 → 必传 | 证明不了 → 选填 |
|---|---|
| 井盖缺失、路灯不亮、垃圾满溢、护栏断裂、路面破损、积水漏水 | 网络卡顿、断网、系统故障、噪音扰民 |
| 看图就能确认"这儿确实有问题" | 拍出来只是一台正常的路由器，或一个没有异常的角落 |

规则写在 `shared/domain.js` 里，一处定义两端共用：

```js
var PHOTO_OPTIONAL = { network: 1, other: 1 };
function photoRequired(typeId) { return !PHOTO_OPTIONAL[typeId]; }
```

选填时界面上给一句「上传图片能够更快的解决问题」，不催、不拦。
无图提交跳过视觉闸门，只走语义判断，但描述要求 ≥ 4 字（`no-info`），
否则一条"有故障"进来，谁都不知道是什么故障。

### 矛盾确认：以图为准，但让人点头

用户选了「照明路灯」写"这盏灯不亮"，照片里却是一个塌了的井盖。这时候硬提交会把工单派给水电班组，
水电师傅跑一趟发现该找基建处——这是最典型的浪费。

判定成立要满足三个条件（缺一不可）：**有原图、模型真看了、模型说对不上**。
少任何一个都只是"建议"，不弹窗。

成立之后弹一个两列对比：左边【你填的】，右边【照片里是】，外加模型重写的描述。
三个按钮：**按这版提交 / 保留我的描述 / 取消**。

- 按这版 → 类型和描述一起换掉，`conflictAction: 'applied'`
- 保留我的 → 原样提交，但工单标 `review`，后台抽屉里写明"你选择保留原描述，已转人工重点核对"

为什么不直接静默改？类型错了改类型没有信息损失，**描述是用户自己写的话**，改掉它等于替他重新陈述事实。
这一处必须留一个"我不同意"的出口。

### 即时预判：图一进来就干活

按下快门之后、还在想怎么描述的那几秒，是用户最容易放弃的时候。这段时间做两件事：

1. 认出这是哪一类，把候选类型顶在类型区下面：「AI 看这张图，像是这一类 · 安全隐患」，点一下换过去；
2. 写一句现成描述：「你可能想上报：图书馆南侧路面井盖缺失，坑口外露」，点一下填进输入框。

`max_tokens: 220`、`temperature: 0.1`，只要四个字段 `{isFacility, type, desc, confidence}`。

**拿不到结果就什么都不显示**——不猜、不兜底、不放一句"看起来像设施问题"。
猜错类型比不猜更糟：用户会以为系统认定了，反而不敢改。演示用的 SVG 插画也不送，
那不是"照片"，送过去只能得到一句瞎猜。

### 三种运行模式

```js
createAgent({ mode: 'auto' })      // 有 Key 走 DeepSeek，失败自动回落规则
createAgent({ mode: 'rules' })     // 纯本地规则，答辩断网也不翻车
createAgent({ mode: 'deepseek' })  // 强制走模型
```

**降级策略是放行而不是拒绝**：模型超时 / 报错 / 没配 Key，返回 `pass: true, degraded: true`，
工单标记为「待人工复核」。宁可让管理员多看一眼，也不能让人拍完照发现提交不了。

## 五、防刷：提交闸门（Guard）

一个人十分钟里连报二十条，不管是手滑、赌气还是刷积分，都会把真正急的单子挤下去。
`shared/guard.js`，约 200 行，零依赖，**写在提交按钮前面**，不是事后统计。

先说清楚它拦不住谁：这是纯前端 + localStorage，改代码的人一定拦得住自己被抓。
所以目标不是"防黑客"，是拦住**正常用户的重复提交和情绪化刷屏**，并把异常记下来给管理端看。

五道规则，从轻到重：

| 规则 | 阈值 | 拦的是什么 |
|---|---|---|
| 间隔 | 25 秒 | 手滑连点、网络卡了重复点 |
| 同图 | 同一张照片 24 小时内只能用一次 | 拿一张图换地址刷分 |
| 重复 | 同类型 + 80 米内 + 10 分钟 | "以为没提交成功"又报一遍 |
| 配额 | 10 分钟 4 条 · 1 小时 12 条 | 情绪化刷屏 |
| 冷静期 | 连续 3 次被 AI 拦下 → 停 5 分钟 | 拿系统当"试探 AI 底线"的玩具 |

**"同一处重复"是直接告诉用户，不是默默合并。** 这看着反直觉，但合并更糟：
人看不到反馈，会以为没提交成功，于是再报一次，然后再一次。

### 照片指纹怎么算

限流拦得住"报得快"，拦不住"拿同一张图报十次"——那才是刷积分最省事的路子，
不用出门，改个地址就行。

`Guard.hashImage()` 做 8×8 灰度平均哈希，输出 16 位十六进制：

- **只存指纹，不存原图**。一条记录约 148 字节，够比对，也不构成隐私负担；
- 比对用**汉明距离 ≤ 8 位（64 位里）**，不是严格相等。
  同一张照片过一遍微信再存下来、手机端缩到 1100px 而网页版原样读取，
  指纹会漂几个 bit；要求相等等于规则形同虚设；
- 只给**真拍/真传**的图算指纹。演示用的示意图是所有人共用的素材，
  算出来必然一样，拿它去拦人等于把演示路径堵死；
- 算不出（画布被污染、图太大）就**跳过**。宁可少拦一次，也不能让人因为技术原因报不上。

「AI 拦下 → 转人工复核」这条路也要落指纹，否则它就成了绕开同图判重的口子。

记录保留 25 小时（指纹要回溯一天），限流窗口仍按 1 小时算，两者互不影响。

## 六、合并规则（这块是核心业务逻辑）

同一件事被反复上报，是众包系统的头号噪音来源。但「合并」和「升级」必须分开处理，
否则会被人刷。

`shared/domain.js` 里的判定：

```
半径 15 米 + 时间窗 24 小时 + 同类型  →  合并
```

合并之后是否提升紧急度，看是谁报的：

| 情况 | 处理 | 理由 |
|---|---|---|
| **同一用户**重复上报 | 合并，**不升级** | 一个人报十遍还是一件事，避免单人刷分刷优先级 |
| **多个用户**上报 | 合并，**每多一人 +1 星**（上限 5 星） | 多人独立发现 = 客观上更严重，这是真实信号 |

严重度到紧急度的映射：

| 星级 | 等级 | 标记 |
|---|---|---|
| 5 | P0 | 紧急 |
| 4 | P1 | 高 |
| 3 | P2 | 中 |
| 2 | P3 | 较低 |
| 1 | P4 | 低 |

## 八、地图

没有用 Leaflet，也没有用高德 JS SDK，自己写了约 500 行 `shared/tilemap.js`。

原因很实在：本项目的地图只做三件事——铺瓦片、打点、画热力。引入整套 SDK 要多背 200KB，
还要处理它和项目风格的冲突。自己写反而更轻、更好改。

实现要点：

- **墨卡托投影 + 瓦片金字塔**，瓦片源用高德（`gaode` 常规 / `satellite` 卫星 / `plain` 纯路网）
- **WGS-84 → GCJ-02 坐标纠偏**。这一步不能省：国内地图瓦片是 GCJ-02 体系，
  直接拿 GPS 原始坐标往瓦片上画，所有点会整体偏移 300–600 米。
  坑在于这个转换**不是全局做一次就行**——投影原点每次重算都要先转换再投影，
  早期版本就是把原点存成了 WGS-84，结果所有标记挤在地图右边缘。
- **标记聚合**：屏幕像素距离小于 30px 的点自动合成一个带数字的簇，校园里点位密集时不糊成一片
- **热力层**：`globalCompositeOperation = 'lighter'` 做透明度累加，再用 `getImageData` 查色带映射颜色

坐标在用户端展示时还会做 **±15 米抖动**（`fuzz()`）——精确坐标约等于暴露具体位置，
管理端拿到的是原始坐标用于派单，用户端只给大致范围。

## 九、管理后台

四个视图，侧边栏可收起（给投影和笔记本小屏留空间）。

- **看板**：真实地图热力图（按类型着色、可切图层）、高频片区 Top5、7 天趋势、AI 拦截率
- **工单**：类型/部门筛选、5 种排序、现场缩略图、AI 诊断摘要、合并组标记、**待复核队列**、详情抽屉、导出
- **派单**：按责任部门分组，看每个班组手上有多少活
- **洞察**：AI 生成周报、巡逻路线建议、同类工单合并建议

### 待复核队列

「待复核」不是一个状态装饰，是一个**要有人处理的收件箱**。

进入 `review` 的单子来自四个地方：画质存疑（`blur`/`dark`）、AI 拿不准、图文矛盾但用户坚持原描述、
用户主动点了「转人工」。这些单的共同点是——**机器不敢下结论，但人一眼就能**。

所以给它们一条专门的通道：

- 表格上方一条提示：「N 条在等人工复核」，筛选栏的「待复核」带数字徽标
- 抽屉打开第一屏就是复核区，**排在 AI 诊断前面**——值班的人打开抽屉就是为了点那两个按钮
- 复核区摆四样东西：复核原因、用户原话、AI 看到什么、类型被改成了什么（以及为什么）
- 两个按钮：**确认有效** → 转 `processing` 并派单；**驳回** → `rejected`，不进派单
- 两个动作都写时间线与编码表，用户端刷新就能看到

抽屉里如果这张单**本应附照片却没有**（类型要求必传的那几种），会说"别直接派人空跑"；
如果类型本来就允许不传，则说"这一类允许不传照片"，不吓唬人。

### AI 洞察：数字本地算，判断交给模型

周报、巡逻路线、合并建议三块，曾经是把统计数字套进固定句子——"本周共受理 N 条，其中 M 条为…"。
那不算 AI，那是模板。

现在分工明确：

| 谁 | 做什么 |
|---|---|
| 本地 | 算清所有数字（环比、Top 类型、积压时长），拼成一行"事实"摆在最上面 |
| 模型（`shared/insight.js`） | 只做判断：这周真正的问题是什么、巡逻该先去哪三个点、哪些单子像同一件事 |

**模型挂了就说挂了。** 周报区显示「AI 没有连上，周报没有生成」，
下面给两条启动命令，并说明"本地代理没启动时，后台不会用固定模板假装是 AI 写的"。
合并建议区退化成"只按位置聚类，不构成建议"。数字条仍然是真数字。

这比"降级成看起来像 AI 的文本"重要得多——**一份假周报比没有周报危险**，
因为看的人会拿它去做决定。

### 现场模式

顶栏那个红点按钮。点开之后**所有演示数据立刻清空**，看板只接现场真报上来的工单：

- 手机上报一条，投屏上的看板两秒后自动长出这条（`localStorage` 轮询，不需要后端）
- 抽屉里能看到**现场原图**、AI 判定来源（DeepSeek / 本地规则）、五项图像指标
- 点「办结并发分」= 确认"人到过现场、问题真解决了"，同时把积分发给上报人
- **清空工单 / 撤销清空**：讲完一页想换一屏，点一下就清；清错了点撤销原样回来。
  清空只把工单从看板摘下来，不动 `localStorage` 里的编码表（用户报的单子是真数据，
  删了他就查不到进度了）。被清掉的编码会被临时挡住，否则两秒轮询又把它们捞回来。
- 退出即恢复演示数据

### 工单进度

每张工单带一条 `timeline`，节点结构是「谁 + 什么角色 + 做了什么 + 细节 + 这一步之后的状态」：

```js
{ at, label: '已到场核实', by: '水电班组 · 李师傅', role: 'crew',
  note: '确认镇流器烧损，需回库领件', state: 'processing', tone: '' }
```

- 用户端「我的上报 → 详情」按时间轴展示，带角色徽章、操作方、备注、以及**距上一步多久**
- 后台抽屉展示同一份数据，并多一块编辑区：快捷动作（已到场 / 材料未到 / 处置中 / 已修复 / 需延期 / 已转派）+ 自定义备注
- 后台记的进展会写回编码表，手机端刷新就能看到——不是两套数据
- 受理、办结这两个列表动作也会自动补节点，不需要再单独记一条

节点只增不改，是这张单唯一的事实来源。累积用时直接由首尾时间算，不做额外字段。

答辩时最尴尬的一幕是"刚收到一条上报"配上早就准备好的假数据。这个模式就是为了让那句话说出口时，屏幕上真的只有一张单子。

### 排序

默认 **紧急度优先**（P0 → P4），另有：

- 反馈人数优先（合并人数多的排前面）
- 最新上报在前 / 最早上报在前
- 按负责部门分组

### 导出

按钮点下去直接下载 CSV（**带 UTF-8 BOM**）。

这里刻意没用「HTML 伪装成 .xls」的野路子——那个方案 Excel 打开会弹「文件格式与扩展名不一致」的警告，
答辩现场弹一次就够尴尬的。CSV + BOM 是 Excel 双击不报警、中文不乱码的最小代价方案。

### 高频片区统计的一个坑

早期版本按**完整地址**分组，结果排行榜全是「1 条」——因为「图书馆南广场路灯」和「图书馆南广场坡道」
被算成两个地方。现在用 `areaOf()` 先提取片区关键词（图书馆南广场、柳园宿舍区、核心教学区……），
再聚合，排行榜才有意义。

## 十、材质：Liquid Glass

整体用了液态玻璃风格，`admin-web/assets/admin.css` 里是一套完整的 `.glass` 系统。

真正的玻璃感需要四个条件同时成立，缺一个就变成"半透明灰色方块"：

1. **背景得有东西可透** —— 页面底层铺了彩色光晕，玻璃才有内容可以模糊
2. **半透明白 + `backdrop-filter: blur() saturate()`** —— 模糊负责磨砂，饱和度负责让透出来的颜色不发灰
3. **1px 高光边框** —— 用 `mask` 技巧做出只有上边缘亮的渐变描边
4. **大半径柔和阴影** —— 半径大、透明度低，才像悬在空中的玻璃板

还有个 CSS 陷阱值得记一笔：入场动画用 `animation-fill-mode: both`，
而 keyframes 只声明了 `from` 没声明 `to`，元素会**永久停在起始帧**（透明度 0，等于隐身）。
必须用 `backwards`，让默认样式本身就是最终态。

## 十四、几个刻意的取舍

**1. AI 挂了要放行，不是拒绝**
见上文降级策略。用户端体验优先于数据纯净度——数据脏了可以人工筛，人走了就回不来了。

**2. 单人重复上报不给奖励**
合并但不升级严重度。任何"多报多得"的设计，最后都会被一个人刷穿。

**3. 管理端不做成"手机界面拉宽"**
信息架构完全不同：手机端一次只做一件事，管理端要同时对比表格和多张图。最小宽度 1200px 是有意的。

**4. 所有 AI 结论旁边都有人工出口**
每个判定都写着「仅供参考」，都能手动改。模型会误判，这是事实。

**5. 不引第三方地图 SDK**
只为铺瓦片打点，不值得背一整套 SDK。

**6. 积分不在提交时发，也不做宠物养成**
这两条是一个取舍的两面：积分只用来奖励"帮上了忙"，不用来制造黏性。
AI 放行就发钱，等于奖励会拍照的人；养一只宠物天天喂，等于让积分变成另一个游戏的货币。
两样都会把注意力从"问题有没有被解决"上挪开。

**7. 宁可说"AI 没连上"，也不编一段出来**
周报、巡逻路线、合并建议、提交摘要，全都只认模型的返回值。模型没接上就明说没接上，
并告诉人怎么把代理启起来——数字照常显示，判断留空。

一份看起来像 AI 写的假周报，比没有周报危险得多：看的人会拿它去做决定。
同理，类型选错不再驳回、照片可以不传，也都是同一个取舍——**减少让人白跑一趟的环节**，
但绝不为了"通过率好看"去伪造任何结论。

## 十五、已知限制

- **`file://` 下拿不到定位**，浏览器安全策略决定的，不是代码问题。要完整体验请走 `node server/proxy.mjs`
- **游客身份只存在本机**，清掉浏览器记录就换人了；跨设备可追溯的只有查询编码
- **GitHub Pages 上 AI 走规则模式**：静态托管没有服务端，密钥没法藏，所以线上只跑本地规则；
  要真跑视觉判定就 `node server/proxy.mjs`，或把转发层放到云函数上
- **演示样例图是 SVG 插画**，视觉模型会正确判定"这不是照片"，所以样例图走指标 + 规则，
  只有实拍照片才走视觉判定——这不是 bug，是刻意的分流
- **夜间照片仍然难**：模型能看出"路灯不亮"，但曝光不足时细节少，严重度容易打低一档
- **合并只看坐标和类型，不看图片内容**，同一位置两盏不同的灯可能被误合（合并时保留全部照片供人工判断）
- **用户端数据是本地模拟**，刷新即重置；接真实后端需要把 `data.js` 换成 API 调用
- **热力图配色在浅色背景上偏淡**，深色模式下更清楚
- **提交闸门是前端约束，不是安全边界**：`jw.guard.v1` 存在 localStorage，会写代码的人一定绕过得了。
  它挡的是手滑、赌气和情绪化刷屏；真要防刷分，得在服务端按设备/身份做同一套规则
- **照片指纹只在一个浏览器里有效**：换设备、换浏览器、清缓存都是新账本。
  指纹本身也是概率性的（8×8 平均哈希，允许 8 位漂移），极端情况下会误判或漏判
- **复核队列要求人真的去点**：没有超时升级机制，没人看就一直挂在「待复核」
