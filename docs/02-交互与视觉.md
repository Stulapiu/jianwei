# 页面、交互与视觉规范

## 一、页面清单

### 用户端（微信小程序）

| 页面 | 路径 | 核心任务 |
|---|---|---|
| 首页 | `pages/index` | 看地图、找问题、一键上报 |
| 上报 | `pages/report` | 拍照 → 定位 → 选类型 → 提交 |
| 结果 | `pages/result` | 成功反馈 / AI 拦截反馈 |
| 我的上报 | `pages/my-reports` | 按状态查历史 |
| 我的 | `pages/profile` | 信用分、徽章、入口 |
| 徽章墙 | `pages/badges` | 六枚徽章的获得条件 |

### 管理端（PC Web）

| 视图 | 核心任务 |
|---|---|
| 数据看板 | 热力图、Top5、趋势、拦截率 |
| 工单管理 | 筛选、查看 AI 诊断、状态流转、导出 |
| AI 参谋 | 周报、巡逻路线、合并建议 |

**管理端不是把手机界面拉宽**。信息架构完全不同：手机端是「单任务单屏」，管理端是「多信息密集对比」。最小宽度 1200px，表格 `min-width: 1000px` 支持横向滚动，看板用 CSS Grid `repeat(4, 1fr)` 自适应。

## 三、动效规范

核心原则：**用弹簧曲线，不用线性**。全站只有一条缓动曲线：

```css
--spring: cubic-bezier(0.34, 1.56, 0.64, 1);
```

这个曲线的控制点在 1 之外，会产生轻微过冲再回落，也就是「回弹感」。

| 场景 | 实现 | 时长 |
|---|---|---|
| 按钮按压 | `hover-class` + `transform: scale(0.94)` | 320ms |
| 页面元素入场 | `fadeUp`：translateY(28rpx) + opacity | 520ms，逐个延迟 60ms |
| AI 分析遮罩 | `pop`：scale 0.4 → 1.08 → 1 | 420ms |
| 成功打勾 | `pop` + 外圈 `ripple` 扩散 | 620ms |
| 地图提示卡 | `fadeUp` | 420ms |
| 红点呼吸 | `breathe`：scale 1 → 1.06 | 2s 循环 |
| 徽章点亮 | `pop` | 560ms |
| 拦截页三点 | `dotJump`：上下 10rpx | 1.4s 循环，错开 160ms |

### 两个技术限制的诚实说明

**1. 原生 map 的 marker 不能做 CSS 动画**

微信 `map` 是原生组件，`marker` 只能用 `iconPath` 指定静态图片，无法挂 CSS 动画。所以「红点 scale + opacity 渐入」在原生地图上做不到。

替代方案：
- 本项目用**带光晕的静态图标**（`tools/gen-icons.js` 生成），视觉上接近渐入效果
- 更强的做法是用 `cover-view` 叠加点位，但需要 `MapContext` 做坐标转换，复杂度高，10 天周期不划算
- 如果一定要动画，只能放弃原生 map，改 canvas 自绘地图

**2. 小程序不支持自定义页面转场**

`wx.navigateTo` 的转场是系统原生的，改不了。所以「fade + slide」是通过**页面内元素逐个入场**营造的：页面一进来，标题、卡片、按钮按 60ms 间隔依次浮现，观感上就是一次淡入上滑。

### Lottie 的取舍

需求里提到用 Lottie 做成功动画。实际实现用的是纯 CSS 绘制的打勾 + 光晕扩散，原因：

- Lottie 需要 `lottie-miniprogram` + canvas 渲染层，包体积增加约 200KB
- 一个打勾动画用 CSS 只要 15 行，效果差异在手机上几乎看不出来

如果后期要做复杂的信封飞出动画，再引入 Lottie 也不迟，`pages/result` 的动画容器已经预留好了。

## 四、AI 标签规范（硬约束）

需求里的约束条件，落实到每一处：

1. **所有 AI 结论必须带标签**：统一用 `.tag-ai`，文案固定为「AI 建议 · 仅供参考」
   - 小程序端：结果页的 AI 摘要、处置建议
   - 管理端：工单表的 AI 诊断列、AI 参谋的生成结果
2. **必须保留人工入口**
   - 用户端：拦截页的「仍然提交，转人工复核」
   - 管理端：工单状态可任意流转，AI 建议不锁定操作
3. **AI 不下最终结论**：徽章、信用分由规则结算，不是模型打分决定

## 五、微文案（这是产品的性格）

拦截是负面时刻，文案决定用户会不会再来。

| 场景 | ✅ 这样说 | ❌ 不这样说 |
|---|---|---|
| 照片模糊 | 这张照片有点模糊，换个角度或者靠近一点再拍一张？ | 照片不合格 |
| 不是设施 | 这张图里好像没有看到公共设施，是我们看漏了吗？ | 未检测到目标物体 |
| 类型冲突 | 你选的是「照明」，但描述说的好像是另一类问题，确认一下类型？ | 类型与内容不匹配 |
| 合并 | 已有邻居上报过这里，已合并为同一工单 | 重复提交 |
| 被拦 | 这次不算你的错，只是 AI 想让工单更准确一点 | 提交失败 |

三条原则：

1. **不指责**：问题出在照片上，不出在人身上
2. **给下一步**：每个否定都附带「怎么办」
3. **留退路**：任何拦截都有「仍然提交」

## 六、状态设计

每个页面都要考虑四种状态，缺一个就会在演示时露馅：

| 状态 | 处理 |
|---|---|
| 加载中 | 骨架或 `fadeIn` 的浅色提示条，不用转圈 loading |
| 空 | 顶部一个淡绿圆点 + 一句话 + 一个行动按钮（如「去上报一个」） |
| 失败 | 不用红色报错，`console.warn` + 静默降级，顶部保留可用内容 |
| 无权限 | 定位失败时降级为手动填地址，不阻断流程 |

`pages/my-reports` 的空状态就是这么做的：不写「暂无数据」，而是「还没有上报记录」+「去上报一个」按钮。

## 七、可访问性要点

- 所有可点区域高度 ≥ 88rpx（约 44pt，iOS 最小触控标准）
- 正文与背景对比度 ≥ 4.5:1（`#1A2624` on `#F7F9F9` 约为 13:1）
- 不依赖颜色单独传递信息：状态除了红/绿，都带文字标签
- 动效不影响功能：即使关掉动画，所有流程依然可完成
