# AI 处理中枢设计

## 一、三级降噪漏斗

```
用户提交
   │
   ├─ 闸门 1 · 视觉理解 ──── 清晰度 / 是否含设施 / 与类型一致
   │         ↓ 不通过 → 温和提示 + 记 1 次无效
   ├─ 闸门 2 · 文本语义 ──── 描述与类型是否冲突 → 产出严重度 + 摘要
   │         ↓ 不通过 → 提示「确认一下类型？」
   ├─ 闸门 3 · 坐标去重 ──── 15 米 / 24 小时 / 同类型 → 合并进已有工单
   │
   └─ 通过 → 生成工单 + 处置建议
```

**为什么视觉在文本前面**：图不对，文字写得再准确也没意义。先拦掉 60% 的垃圾，再让文本模型做精细判断。

**为什么两道闸门并行**：视觉和文本互不依赖，`Promise.all` 之后总耗时取较慢的那个（约 4–8 秒），而不是相加（10–16 秒）。用户不会愿意等十几秒。

## 二、提示词设计

完整提示词在 `cloudfunctions/aiSentinel/index.js` 的 `VISION_SYSTEM` / `TEXT_SYSTEM`。几个关键点：

### 1. 把判定维度拆成可枚举项

不要问模型「这张图行不行」，它会给出一堆模棱两可的话。要给它具体的检查清单：

```
必须从三个维度判断：
1. 清晰度 clear：严重失焦、过暗、过曝、大面积遮挡，都算不清晰
2. 主体性 facility：路灯、垃圾桶、井盖、护栏… 自拍、风景、截图、表情包都不算
3. 类型一致性：用户选了照明，画面主体应当与灯具有关
```

### 2. `reason` 限定为枚举值

```json
{"reason": null | "blur" | "not_facility" | "type_mismatch"}
```

只有把输出限制成有限集合，前端才能映射到具体的引导文案。如果让模型自由发挥，你永远不知道它下一次会输出什么。

### 3. 让模型直接写出给用户看的话

```
message 是给普通居民/学生看的，必须温和、不指责、给出可操作的下一步，
例如「这张照片有点模糊，换个角度试试？」而不是「照片不合格」。
```

这是把「共情」写进提示词，比在前端硬编码几十条文案更灵活，也更贴合实际画面。

### 4. 严重度给出锚点

```
5 = 有即时人身危险（井盖缺失、电线裸露、护栏断裂）
4 = 影响安全或大面积使用
3 = 影响正常使用
2 = 影响体验但不紧急
1 = 建议性改进
```

不给锚点，模型永远打 3 分。给了锚点，5 分才真的代表「必须今天处理」。

## 三、可靠性设计

这一节比提示词更重要 —— 模型一定会出问题，关键是出问题时系统怎么表现。

### 1. JSON 解析失败 → 三级兜底

```js
// chatJSON 里的处理顺序
1. 直接 JSON.parse
2. 失败 → 剥掉 ```json 代码块再试
3. 再失败 → 截取第一个 { 到最后一个 } 再试
4. 全失败 → 抛错，由调用方决定降级
```

不静默返回脏数据。解析不了就是解析不了。

### 2. 模型超时/报错 → 明确失败，不降级

```js
catch (err) {
  return { pass: false, stage: 'ai', aiFailed: true }
}
```

**AI 是必经路径，不是可跳过的辅助**。模型服务挂了，这一单就明确"没有分析"，不落库、
不生成摘要，表单和照片原样保留，用户点重试即可。

早期版本这里是 `pass: true, degraded: true`（降级放行）。删掉的原因是它会产生一批
"看起来分析过、其实没看图"的工单：演示时分析内容和照片明显不符，值班的人也会误判。

### 3. 没有 API Key → 健康检查直接说不行

`/health` 返回 `ok: false`（`hasKey: false`），前端显示「AI 未连接 · 点此重试」，
提交时直接拦下。没有本地规则引擎冒充判定结果。

| 状态 | 表现 |
|---|---|
| 代理没启动 | 探活失败 → AI 未连接 |
| 代理起了、没 Key | `ok:false` → AI 未连接 |
| 有 Key、模型超时 | 提交失败 → 提示重试，不落库 |

### 4. 拦截页的出口

- **本地画质没过**（糊、暗、空白、截图）：只有「重新拍一张」，没有"仍然提交"。
  一张看不清的图放进复核池，只会让复核的人替用户重拍一次。
- **模型判定没过**（不是设施、画面无内容）：保留「仍然提交，转人工复核」。
  这类是模型真的看过了、给出了判断，用户可以不同意。

> 产品的底线是：本地决定"能不能看"，模型决定"看到了什么"，人保留最终否决权。

## 四、成本估算（量级参考）

以通义千问为例，一条上报的调用成本大致是：

| 环节 | 模型 | 每次 token 量级 |
|---|---|---|
| 视觉判定 | qwen-vl-max | 输入约 1k（含图），输出约 100 |
| 文本判定 | qwen-plus | 输入约 200，输出约 80 |

按公开价目粗略折算，**单条上报的 AI 成本在 1–3 分钱之间**。一个 5000 人的校园，日均上报 50 条，一个月的 AI 花费在几十元量级。

要压成本，三个杠杆：

1. 图片先压缩（小程序端 `sizeType: ['compressed']` 已经做了），1024px 足够判断
2. 视觉用轻量模型（`qwen-vl-plus` 比 `max` 便宜一个数量级），只在置信度低时升级到强模型
3. 加本地前置过滤：图片小于 30KB 直接判模糊，不用调模型

## 五、换模型怎么改

只改一个文件：`cloudfunctions/*/aiProvider.js` 的 `PROVIDERS` 配置。

```js
const PROVIDERS = {
  dashscope: { url: '...', keyEnv: 'DASHSCOPE_API_KEY', textModel: 'qwen-plus', visionModel: 'qwen-vl-max' },
  zhipu:     { url: '...', keyEnv: 'ZHIPU_API_KEY',     textModel: 'glm-4-flash', visionModel: 'glm-4v-flash' },
  deepseek:  { url: '...', keyEnv: 'DEEPSEEK_API_KEY',  textModel: 'deepseek-chat', visionModel: null }
};
```

三家都兼容 OpenAI 的 `/chat/completions` 协议，所以请求逻辑完全复用。DeepSeek 没有视觉能力，代码里做了自动改道：视觉请求自动转给通义，文本仍走 DeepSeek。

**已注意的坑**：微信云开发每个云函数独立打包，不能 `require('../aiProvider')`。所以 `aiSentinel` 和 `genReport` 各有一份 `aiProvider.js`，改的时候两边都要改。

正式项目里可以用构建脚本同步，或者把它发成一个独立云函数被其他函数调用（会多一跳网络，原型期不划算）。

## 六、环境变量配置

云开发控制台 → 云函数 → 选中函数 → 配置 → 环境变量：

| 变量名 | 值 | 说明 |
|---|---|---|
| `AI_PROVIDER` | `dashscope` | 或 `zhipu` / `deepseek` |
| `DASHSCOPE_API_KEY` | `sk-xxx` | 阿里云百炼控制台获取 |
| `ADMIN_OPENIDS` | `oXXXX,oYYYY` | 管理端权限，逗号分隔 |

不配 `AI_PROVIDER` 默认走通义；不配 Key 自动进 mock 模式，功能和演示都正常。

> 密钥只放环境变量，不要写进代码。这个项目会开源给别人看，写死的 Key 会在几分钟内被扫走。

## 七、已知局限（诚实版）

写在这里，是为了答辩时被问到能答上来：

1. **视觉模型对夜间照片判断不稳定**。路灯损坏多发生在晚上，而夜景照片本身偏暗，模型容易误判为「过暗不清晰」。缓解办法：提示词里明确「夜间拍摄的路灯照片，以能否看清灯具轮廓为准」。
2. **文本一致性判断对极简描述无效**。「坏了」这种描述既不冲突也不提供信息，只能放行。这类工单靠人工补全。
3. **去重只看坐标和类型，不看图片**。同一个垃圾桶的正面和背面会被合并，这个可以接受；但「同一条街两盏不同的灯」也可能被误合并。缓解办法：合并时保留所有照片，让管理员在详情里看到全部。
4. **严重度打分是模型主观判断**，不同模型版本之间会漂移。所以看板上标注了「AI 建议 · 仅供参考」，并且合并逻辑用 `max()` 而不是求和，避免分数被堆高。
