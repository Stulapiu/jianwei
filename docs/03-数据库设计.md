# 云数据库表结构设计

云开发用的是文档型数据库（MongoDB 内核），和 MySQL 的思路不一样，这里先把设计原则讲清楚，再列字段。

## 一、三个设计决策

### 1. reports 是事实源，orders 是聚合视图

一条工单可以挂多条上报。这样「多人反馈，紧急度高」不需要靠冗余字段模拟，而是天然成立：

```
reports (N) ──── orderId ────→ orders (1)
```

用户端「我的上报」读 reports，管理端工单列表读 orders。合并发生时只改 orders 的 `reportIds` 和 `mergeCnt`，reports 一条都不动，历史记录完整保留。

### 2. 坐标存两份：精确的给派单，模糊的给展示

| 字段 | 精度 | 谁看 |
|---|---|---|
| `lat` / `lng` | 原始 GPS（约 5–10 米） | 管理端派单、热力图 |
| `locFuzzy` | 四舍五入到小数点后 3 位（约 100 米网格） | 用户端地图红点 |

乡村场景尤其重要：一个村可能就几十户，精确坐标等于暴露住户位置。用户端接口 `mapPoints` 只返回 `locFuzzy`。

### 3. 所有集合都不开放客户端读写

集合权限统一设为「仅创建者可读写」，但实际全部读写都走云函数。云函数带管理员权限，客户端拿不到任何越权能力。

> 这一条是安全底线。如果为了省事把 orders 设成「所有人可读」，管理端数据就暴露了。

## 二、集合字段

### users · 用户

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | string | 主键 |
| `_openid` | string | 微信 openid，云开发自动写入 |
| `nickName` | string | 昵称，默认「热心居民」 |
| `avatar` | string | 头像 URL |
| `credit` | number | 信用分，初始 100，下限 60 |
| `validCnt` | number | 有效上报累计 |
| `invalidCnt` | number | 无效提交累计（AI 拦截 + 人工驳回） |
| `sanitationCnt` | number | 卫生类有效上报数，用于「清道夫」徽章 |
| `streak` | object | `{ days: number, last: 'YYYY-MM-DD' }` 连续上报 |
| `badgeList` | string[] | 已获得徽章的 code 数组 |
| `createdAt` | Date | |
| `updatedAt` | Date | |

信用分规则（写在 `submitReport` 里）：

- 有效上报 `+2`，上限 100
- AI 拦截的无效提交 `-1`，下限 60
- 人工驳回 `-5`（本期未实现，接口预留）

> 下限设为 60 是有意的：不能让用户因为几次误判就被扣到负分然后彻底流失。激励体系的第一原则是别把人赶走。

---

### reports · 上报记录（事实源）

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | string | 主键 |
| `_openid` | string | 上报人 |
| `files` | string[] | 云存储 fileID，最多 3 张 |
| `lat` / `lng` | number | 精确坐标（gcj02） |
| `locFuzzy` | object | `{ lat, lng }` 脱敏坐标 |
| `address` | string | 地址文本，用户可编辑 |
| `type` | string | `lighting` / `sanitation` / `facility` / `safety` / `other` |
| `desc` | string | 用户描述，截断 200 字 |
| `aiVerdict` | object | AI 判定结果，见下 |
| `force` | boolean | 是否为「仍然提交」（用户不认可 AI 判断） |
| `merged` | boolean | 是否被合并进已有工单 |
| `status` | string | `pending` / `processing` / `resolved` / `rejected` / `review` |
| `orderId` | string | 所属工单 |
| `createdAt` | Date | |

`aiVerdict` 内嵌结构：

```js
{
  pass: true,          // 是否通过
  severity: 3,         // 1-5
  summary: '路灯不亮，影响夜间通行',
  advice: '建议排查线路老化',
  reason: null,        // blur / not_facility / type_mismatch
  scene: '夜景拍摄的照明设施',
  provider: 'dashscope',
  degraded: false      // 模型调用失败时为 true（已降级放行）
}
```

> 把 AI 结论内嵌在 reports 里，而不是单独建表：一条上报必然对应一次判定，一对一到没必要拆表，读的时候也少一次查询。

---

### orders · 工单（聚合视图）

| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` | string | 主键 |
| `orderNo` | string | 展示用工单号，如 `WO11243021` |
| `type` | string | 同 reports |
| `lat` / `lng` | number | 精确坐标，用于派单 |
| `locFuzzy` | object | 脱敏坐标 |
| `address` | string | |
| `reportIds` | string[] | 关联的上报 ID 列表 |
| `mergeCnt` | number | 合并了几条上报 |
| `multiFeedback` | boolean | `mergeCnt >= 2` 时为 true |
| `severity` | number | 1-5，多人反馈时自动提升 |
| `summary` | string | AI 摘要 |
| `aiAdvice` | string | AI 处置建议 |
| `status` | string | `pending` / `processing` / `resolved` / `review` |
| `handler` | string | 处理人 |
| `note` | string | 处理备注 |
| `createdAt` / `updatedAt` / `resolvedAt` | Date | |

紧急度提升规则（`submitReport` 内）：

```js
severity = min(5, max(已有工单紧急度, 本次上报紧急度) + (mergeCnt >= 3 ? 1 : 0))
```

即：**三个人以上反馈同一个问题，紧急度自动加一星**。这是众包信号转化为优先级的最简单方式。

### badges · 徽章定义

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | string | 唯一标识，如 `eagle_eye` |
| `name` | string | 「火眼金睛」 |
| `icon` | string | emoji 或图片 URL |
| `rule` | object | 触发条件描述，便于扩展时阅读 |
| `desc` | string | 获得条件的自然语言说明 |

六枚徽章：

| code | 名称 | 触发条件 |
|---|---|---|
| `first_report` | 初次出勤 | 完成第一次有效上报 |
| `eagle_eye` | 火眼金睛 | 上报安全隐患类，且 AI 判定紧急度 ≥ 4 |
| `gold_sentinel` | 金牌哨兵 | 连续 7 天有效上报 |
| `night_watch` | 夜巡者 | 在 22:00–06:00 之间上报 |
| `crowd` | 众人拾柴 | 上报被合并进他人工单 |
| `clean_hand` | 清道夫 | 累计 10 条卫生类有效上报 |

> 判定逻辑在 `submitReport` 的 `BADGE_RULES` 数组里，新增徽章只要加一条规则，不用改流程。

---

### ai_logs · AI 调用审计

| 字段 | 类型 | 说明 |
|---|---|---|
| `scene` | string | `report_verdict` / `weekly_report` |
| `provider` | string | 实际调用的厂商 |
| `mock` | boolean | 是否走了本地降级 |
| `type` / `desc` | string | 判定输入（截断） |
| `pass` | boolean | 判定结果 |
| `reason` | string | 拦截原因 |
| `degraded` | boolean | 是否因异常降级 |
| `latency` | number | 耗时 ms |
| `content` | string | 生成类任务的输出文本 |
| `createdAt` | Date | |

这张表有两个用途，都很重要：

1. **算拦截率**：看板上的「本周拦截 43 条，占比 18%」就是这里统计出来的
2. **反查误判**：用户投诉「我这明明是真问题」，可以拿 `latency`、`reason`、`degraded` 复盘

## 三、索引建议

云开发控制台 → 数据库 → 索引管理，建这几个：

| 集合 | 索引字段 | 类型 | 用途 |
|---|---|---|---|
| `users` | `_openid` | 唯一 | 登录查询 |
| `reports` | `_openid` ↑, `createdAt` ↓ | 复合 | 我的上报列表 |
| `reports` | `status` ↑, `createdAt` ↓ | 复合 | 按状态筛选 |
| `orders` | `status` ↑, `createdAt` ↓ | 复合 | 工单列表主查询 |
| `orders` | `type` ↑, `createdAt` ↓ | 复合 | 去重检测 + 类型筛选 |
| `ai_logs` | `scene` ↑, `createdAt` ↓ | 复合 | 拦截率统计 |

**没有建地理索引**，这是有意的。去重逻辑用「同类型 + 24 小时内」粗筛，再在内存里算球面距离（Haversine）。原因：

- 云开发的 `geoNear` 需要地理索引配合，配置错位时行为不直观，调试成本高
- 原型期工单量在万级以内，一次粗筛最多几十条，内存计算完全够用
- 换成 `geoNear` 时，`submitReport` 的接口签名不用改

数据量上来后（单集合 > 5 万条），把 `nearOrders` 那段换成 `geoNear` 即可。

## 四、初始化步骤

1. 云开发控制台新建 6 个集合：`users` `reports` `orders` `badges` `ai_logs` `patrol_plans`
2. 权限全部选 **「仅创建者可读写」**
3. 按上表建索引
4. 向 `badges` 导入六条徽章定义（可选，前端已内置一份常量兜底）
5. 云函数环境变量配置（见 `docs/04-AI中枢.md`）
